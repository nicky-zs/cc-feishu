# cc-feishu 设计文档

- **日期**：2026-10-15
- **状态**：已确认（设计六节于同日确认）
- **里程碑**：M1 重构迁移 → M2 反向通道（tmux）→ M3 queue/resume + doctor

## 1. 背景与动机

Claude Code 在等待人工响应（Notification hook 触发）时，把生成的内容发送到用户飞书。
现有实现为 `~/.local/bin/notify_feishu.sh`（sh 套 heredoc python，jq 提取 transcript），
已在单机上稳定工作，但存在四个问题：

1. **形态**：sh + heredoc python 不可单测、不可分发，测试只能黑盒 bash 跑
2. **共享**：希望在多台机器的 Claude Code 间共享此能力
3. **演进**：后续要支持反向通道（在飞书回复消息，驱动本地 Claude Code 会话）
4. **上下文**：transcript 提取规则经两次线上 bug 修复才稳定（AskUserQuestion 的
   问题在 tool_use 块；提问时需携带上文），这些规则目前只活在脚本与经验里

### 官方能力调研结论（2026-10-15 已核实）

- Claude Code **没有**官方飞书/Lark 集成（官方 IM 集成仅有 Slack）
- 官方 Remote Control（手机/网页接管本地会话）要求 claude.ai OAuth 订阅，
  **明确不支持 ANTHROPIC_BASE_URL 指向中转/网关的环境**——本工具的运行环境
  恰在此列，故官方远程方案全部不可用
- hooks 体系没有「外部注入输入」类 hook；live 会话注入只剩 tmux send-keys，
  `claude --resume` / `-p` 是官方认可的续跑方式

→ 自建方案没有被官方能力替代。

## 2. 目标与非目标

**目标**

- 飞书侧完整接收 Claude 的输出与提问（含 AskUserQuestion 的问题与选项）
- 反向：在飞书回复（引用）某条通知，驱动本地对应的 Claude Code 会话
- 跨机器共享：pipx 一装，`cc-feishu install` 一注册
- 分片发送遵守飞书限制（post 富文本 30KB/条）

**非目标**

- 不做飞书侧卡片交互 UI
- 不做多用户（只服务单一用户 uid）
- 不替代 lark-cli（它继续作为飞书 OpenAPI 执行层）
- 不支持非 Linux 平台（systemd user unit；tmux 后端依赖 Linux tmux）

## 4. 子命令与数据模型

| 子命令 | 职责 |
|---|---|
| `cc-feishu notify` | hook 入口：读 stdin hook JSON → 提取内容 → 分片 → 发送 → 写路由表。`--dry-run` 打印分片与字节数 |
| `cc-feishu listen` | daemon：消费 im.message.receive 事件流 → 过滤 → 查路由表 → 交付 |
| `cc-feishu install` | 幂等：patch `~/.claude/settings.json` 的 Notification hook；装 systemd user unit；写默认配置。M3 起 queue 后端需要时也注册 UserPromptSubmit hook |
| `cc-feishu doctor` | 体检：lark-cli 可用性、配置、daemon 存活、路由表规模 |

### 路由表（state）

路径 `~/.local/state/cc-feishu/routing.json`，发送通知时写入：

```
message_id → { session_id, tmux_pane?, notify_type, cwd, ts }
```

- `session_id` 取自 transcript 文件名（hook stdin 的 `transcript_path`）
- `tmux_pane` 取自 hook 进程继承的 `$TMUX_PANE`（Claude Code 在 tmux 里跑时自动可用，不在则缺省）
- `notify_type` 仅作信息记录：hook message 含 "permission" 记为 `permission`，否则 `input`（交付后端不据此分支，tmux 注入对两者同样适用）
- TTL 过期清理（默认 24h，可配），防止路由表无限膨胀
- 写入需原子（临时文件 + rename）

### 配置文件（config）

路径 `~/.config/cc-feishu/config.toml`，`install` 生成默认值：

```toml
lark_uid = "ou_..."        # 通知接收人（M1 迁移时从旧 notify_feishu.sh 提取）
chunk_bytes = 12000        # 单片字节预算
from_label = ""            # 通知头 from 行机器标签，缺省用 hostname（替代旧脚本硬编码 IP）；
                           # from 行格式为「标签 (会话短 ID8)」，会话 ID 优先 hook stdin 的
                           # session_id、回退 transcript 文件名（M1 后按用户需求追加）
delivery = "tmux"          # 默认交付后端：tmux | queue
resume_prefix = "/go"      # resume 显式触发前缀
routing_ttl_hours = 24     # 路由表条目过期时间
```

### 通知内容提取规则（transcript.py）

取**最后一段连续的 assistant 条目**，把其中内容按序合并：

- `text` 块：原样
- `AskUserQuestion` tool_use：格式化为 `**标题** 问题（可多选）` + 选项列表（`- 标签：描述`）
- 其他 tool_use / thinking：忽略

条目类型的处理规则（关键，勿改动语义）：

- **assistant** 条目：追加其格式化内容
- **user** 条目（用户输入 / tool_result）：**重置**——这是真正的对话边界
- **其余一切类型**（`last-prompt`/`ai-title`/`agent-name`/`mode`/`permission-mode`/
  `atis-latch`/`system`/`attachment`/`file-history-snapshot` 等元数据）：**忽略**——
  既不追加也不重置

这套规则是三次线上 bug 的修复结论，必须是测试覆盖的核心：
1. AskUserQuestion 的问题在 tool_use 块里——漏掉则通知只有铺垫文本
2. 提问时需携带上文——只取 last 条目则丢失回答问题所需的上下文
3. turn 结束后 transcript 会追加元数据条目——若「非 assistant 即重置」会把正文清空，
   重置必须只认 user 条目

### 分片规则（chunk.py，自现有脚本迁移）

- 每片原始文本 ≤ 12000 UTF-8 字节（`FEISHU_CHUNK_BYTES` 可配），预留 JSON
  转义膨胀与包装余量，保证序列化后低于飞书 post 30KB 上限
- 优先在空行（段落边界）切，其次换行，单行超长才按 UTF-8 字符边界硬切
- 切点落在代码围栏中间时，片尾补 ` ``` ` 闭合、下片重新打开（保留语言标记）
- 多片时第 2 片起头部加 `（续 i/n）` 标记
- 片间发送 sleep 0.3s（避免频率限制）；单片失败只记 stderr 不中断其余片

## 5. 反向通道（transport / routing / delivery 三层分离）

```
transport：lark-cli event consume im.message.receive（NDJSON 流，常驻）
    ↓
routing：回复的 parent_id → 查路由表 → 定位 session / pane
    ↓
delivery（可插拔，逐条选择）：
  ├─ tmux   ：tmux send-keys -t <pane> -l "<文本>" + Enter——主力，全自动
  ├─ queue  ：无 tmux 机器的兜底——写会话待办队列，UserPromptSubmit hook
  │          注入上下文，回到终端提交下一条消息时自动带上
  │          （Claude Code 无外部输入 API，最后一步回车由用户完成——平台限制）
  └─ resume ：回复以 /go 开头显式触发——claude -p --resume <session_id> "<文本>"
             续跑，结果分片发回飞书（会分叉会话，故必须显式触发）；
             异步执行，同一 session 并发 resume 需拒绝并提示
```

设计要点：

- 通知消息里的文本若形如权限选项回复（如 `1`/`2`），经 tmux 后端同样注入
- 未命中路由表的事件、非本人 uid 的事件：忽略
- 将来若切回官方直连/订阅，可新增 Remote Control 后端，核心不动

### 前置验证项（M2 开工前必须实测）

1. **多机事件广播 vs 分流**：两台机器同时 `lark-cli event consume im.message.receive`，
   观察同一事件是都收到（广播 → 各机按 parent_id 归属过滤即可）还是只有一台收到
   （分流 → 需要 relay 单点消费再分发）
2. **自激励回路**：bot 自己发出的通知消息是否触发 receive 事件——若触发，
   listen 必须按 sender 过滤掉 bot 自己的消息

## 7. 安装与分发

- `pipx install git+<repo>` 装载 CLI（Python 零依赖，uv 也是备选）
- `cc-feishu install` 完成集成（hook 注册幂等 patch settings.json、systemd unit、默认配置）
- 更新：`pipx upgrade` + 重启 daemon
- 仓库托管于 GitHub（用户目录 `~/github.com/nicky-zs/`，私有或公开由用户定）
